## 3. 全部问题清单

### 3.1 真实未闭环问题 (7 个)

#### P1-1: luxAutoTarget 全链路缺失

| 项 | 内容 |
|---|---|
| **优先级** | P1 |
| **方向** | 8266 多出 |
| **问题** | 固件支持 `luxAutoTarget` 的 WS 接收、HTTP 接收和 state-report 上报，但后端 4 个 VO/DO 均无此字段，前端无 UI 控件 |
| **影响** | 自动亮度调节的目标值（默认 300 lux）无法远程调整；固件上报的值被后端 Jackson 静默丢弃 |
| **证据** | 固件: `ws_client.cpp:105` 接收, `http_reporter.cpp:133` 上报; 后端: `DeviceStateReportReqVO.java` 无字段, `DeviceDO.java` 无列, `DeviceSaveReqVO.java` 无字段, `DeviceRespVO.java` 无字段, `WebSocketPushService.java:51-79` 不下发; 前端: `types/device.ts` DeviceItem/DeviceCreatePayload 无字段, `LampDeviceCard.vue` 搜索 `lux` 零匹配 |
| **建议** | 后端: DeviceDO 加列 → 4 个 VO 加字段 → pushStateToDevice 加下发 → reportState 加存储; 前端: LampDeviceCard 加滑块 (仅 autoMode 时显示) |

#### P1-2: 设备日志查看 — 用户端前端无入口

| 项 | 内容 |
|---|---|
| **优先级** | P1 |
| **方向** | 前端缺失 |
| **问题** | 后端有完整的日志 API (`/admin/device/logs/query`, `/admin/device/logs/devices`, `/ops-admin/device-logs`)，运维前端 (E:\smart-light-archive) 已实现完整日志查看页面，但用户端前端 (E:\smart-light-front) 无任何日志相关代码 |
| **影响** | 普通用户无法在主前端查看设备日志，必须切换到运维后台 |
| **证据** | 后端: `DeviceLogController.java` 3 个端点, `OpsAdminDeviceLogController.java` 2 个端点; 运维前端: `views/DeviceLogs.vue` (419行完整页面), `api/log.ts` 调用 ops-admin API, `router/index.ts:16` 注册路由; 用户端前端: `src` 目录搜索 `device-log`/`DeviceLog`/`设备日志` 零匹配 |
| **建议** | 在用户端前端添加日志查看入口（可复用运维前端组件），或在设备详情弹窗中嵌入日志面板 |
| **修正说明** | 原报告误判为"前端完全缺失"，实际运维前端已实现。此问题仅针对用户端前端 |

#### P1-3: 固件 register/state-report 字段名不统一

| 项 | 内容 |
|---|---|
| **优先级** | P1 |
| **方向** | 字段不一致 |
| **问题** | 固件 register 消息用短名 `fwVersion`/`fwVersionCode`，state-report 用全名 `firmwareVersion`/`firmwareVersionCode`。后端通过回退读取和别名 setter 兼容，功能无 bug，但增加维护复杂度 |
| **影响** | 后端需维护两套字段名映射；新增字段时容易遗漏兼容 |
| **证据** | 固件 register: `ws_client.cpp:46-47` → `fwVersion`/`fwVersionCode`; 固件 state-report: `http_reporter.cpp:135-136` → `firmwareVersion`/`firmwareVersionCode`; 后端 WS Handler: `DeviceWebSocketHandler.java:300-308` 直接读 `fwVersion` + 回退读 `firmwareVersionCode`; 后端 HTTP: `DeviceStateReportReqVO.java:77-85` 别名 setter |
| **建议** | 固件统一使用 `firmwareVersion`/`firmwareVersionCode`（与后端 DB/VO 一致） |

#### P2-1: luxAutoBrightness 后端不接收

| 项 | 内容 |
|---|---|
| **优先级** | P2 |
| **方向** | 8266 多出 |
| **问题** | 固件在 state-report 中上报 `luxAutoBrightness`（P 控制器计算出的自动亮度值），后端 DeviceStateReportReqVO 无此字段，数据被丢弃 |
| **影响** | 无法在前端查看固件自动调节的亮度值；不影响自动模式本身运行 |
| **证据** | 固件: `http_reporter.cpp:134` 上报; 后端: `DeviceStateReportReqVO.java` 无字段; `DeviceDO.java` 无列 |
| **建议** | 后端加字段接收存储，前端加展示（可选） |

#### P2-2: otaProgress 未持久化到数据库

| 项 | 内容 |
|---|---|
| **优先级** | P2 |
| **方向** | 后端缺陷 |
| **问题** | `DeviceDO` 有 `otaStatus` 字段但无 `otaProgress` 字段。`otaProgress` 仅存在于内存 `OtaProgressStore` (ConcurrentHashMap)，后端重启后进度丢失 |
| **影响** | 后端重启后，正在进行的 OTA 任务进度归零；前端进度条显示异常 |
| **证据** | 后端: `DeviceDO.java` 有 `otaStatus`(行67) 无 `otaProgress`; `OtaProgressStore.java` 用 ConcurrentHashMap 存储; `DeviceRespVO.java:69` 有 `otaProgress` 但通过 `applyProgress()` 动态填充 |
| **建议** | DeviceDO 加 `ota_progress` 列，state-report 时持久化 |

#### P2-3: 固件 config.json 不持久化 luxAutoTarget

| 项 | 内容 |
|---|---|
| **优先级** | P2 |
| **方向** | 固件缺陷 |
| **问题** | `luxAutoTarget` 默认值 300，通过 WS/HTTP 可修改，但重启后恢复默认值 |
| **影响** | 用户调好的光照目标值重启后丢失 |
| **证据** | 固件: `config_manager.cpp:14-31` saveConfig() 只保存 ssid/password/serverHost/httpPort/wsPort; `main.cpp:84` 默认值 300 |
| **建议** | saveConfig()/loadConfig() 中加 luxAutoTarget 持久化 |

#### P2-4: 固件 state-report 不上报灯光状态字段

| 项 | 内容 |
|---|---|
| **优先级** | P2 |
| **方向** | 固件缺失 |
| **问题** | 固件 state-report 上报固件版本、OTA 状态、光照目标等，但不上报当前 brightness/temp/autoMode 等灯光状态 |
| **影响** | 后端 DB 中的灯光状态可能与固件实际状态不一致（依赖 WS state 同步，但 WS 断连时会丢失） |
| **证据** | 固件: `http_reporter.cpp:129-141` 上报字段为 chipId/deviceType/ip/luxAutoTarget/luxAutoBrightness/firmwareVersion/firmwareVersionCode/firmwareChannel/otaStatus/otaProgress，无 brightness/temp/autoMode |
| **建议** | 固件在 state-report 中加 `doc["brightness"] = brightness; doc["temp"] = temp; doc["autoMode"] = autoMode;` |

### 3.2 需求未确认 (2 个)

#### U1: mainColorRgb 固件不处理

| 项 | 内容 |
|---|---|
| **优先级** | 需求未确认 |
| **方向** | 后端多出 |
| **问题** | 后端通过 WS state 下发 `mainColorRgb` 给设备，固件完全忽略（不解析、不存储、不使用） |
| **影响** | 面料主色信息无法在固件端使用 |
| **证据** | 后端: `WebSocketPushService.java:61` 下发; 固件: `ws_client.cpp:89-118` 未读取 mainColorRgb; `app_config.h` 无 mainColorRgb 变量; `include` 和 `src` 目录搜索 `mainColorRgb`/`mainColor`/`main_color_rgb` 零匹配 |
| **需求判断** | ESP8266 灯具是**双色温 LED**（冷白 D2 + 暖白 D1），不是 RGB LED。`mainColorRgb` 是 AI 面料识别的"服装主色"，用于前端展示色块，**灯具硬件不需要此信息**。后端下发属于冗余，不影响功能 |
| **建议** | 如确认灯具不需要 RGB 主色信息，可从 `pushStateToDevice()` 中移除 `mainColorRgb` 下发，减少无用数据传输 |

#### U2: BH1750 P 控制器参数无法远程调节

| 项 | 内容 |
|---|---|
| **优先级** | 需求未确认 |
| **方向** | 固件设计 |
| **问题** | P 控制器的比例系数 (0.1)、读取周期 (2s)、限幅范围 (5-100) 均为硬编码常量 |
| **影响** | 无法远程调优自动亮度响应速度和范围 |
| **证据** | 固件: `sensor_manager.cpp:121-127` 比例系数 0.1 硬编码, 读取周期 2000ms 硬编码, constrain(5,100) 硬编码 |
| **需求判断** | 当前参数对零售场景可能已够用。是否需要远程调优取决于实际部署反馈 |
| **建议** | 先闭环 luxAutoTarget (P1-1)，观察实际效果后再决定是否需要更细粒度的参数调节 |
